Why it exists

Tendering rules differ from one entity to the next. The need to trust the result does not.

Built by KBM for public tendering
A tender is only as trustworthy as the steps nobody was able to skip.

Every entity has its own stages, approval levels, envelopes and eligibility rules, and most tendering systems answer that with a custom build. TenderFlow answers it with configuration: one product, one installation per entity, each running its own cycle from a versioned template. What it will not let anyone configure away is the part that makes a tender defensible: bids stay sealed until the deadline, nobody approves their own work, and every action lands in an audit chain that cannot be edited.

Capabilities

Flexible where it can be.
Fixed where it must be.

The cycle bends to each entity. The safeguards around it do not.

Configurable cycle
Cycle templates · Approval chains · Envelopes

Your process, as a template

Every entity tenders differently. Switch stages on or off, set approval chains of any length, choose one or two envelopes, and decide eligibility by activity code and grade.

Paid documents, gazette / CAPT publication and records lock are options too. Each cycle runs from a versioned template, so a change to the process is a new version, not a rewrite.

One product, configured per entity — not a custom build per entity.
Integrity
Sealed bids · Separation of duties

The rules no configuration can switch off

Bids are encrypted before they are stored and stay sealed until the deadline. Only the committee chair can open them, and only after the tender has closed. Not even the administrators of the content store can read a bid before opening.

Nobody approves their own work: the approver is never the creator, and whoever approves an award is never the person who recommended it.

Configurable where entities differ. Fixed where trust depends on it.
AI assistance
IBM watsonx Orchestrate · 10 advisory agents

Ten agents that draft, check and explain — and decide nothing

A supervisor, the TenderFlow Assistant, coordinates nine specialists: request classifier, pack checker, gazette / CAPT notice drafter, vendor relevance matcher, clarification assistant, grade reviewer, compliance screener, evaluation narrator and document intelligence.

They are advisory by design. The compliance checklist carries no scores, drafts wait for a person to approve them, and an administrator can describe a configuration change in Arabic or English and get a draft that a human still has to publish.

The committee keeps the decision. The agents take the paperwork.
Audit trail

An audit trail that proves itself

Every action is written to an append-only, HMAC-chained audit log. An auditor can verify the whole chain on demand and take away an evidence pack.

Records

IBM FileNet as the system of record

Tender documents live in IBM FileNet Content Manager. An evidence panel shows each document’s object id, class, folder, versions, SHA-256 hash and record status. Addenda become new versions, and records are declared at award.

Document intelligence

Uploads read, classified and cited

Vendor uploads are classified and their data extracted, with citations back to the source document. A person accepts or corrects every value before it is used.

Vendors

The whole vendor relationship, managed

Registration, activity codes and grades, annual subscriptions with renewal reminders, grade upgrades and fee exemptions — plus vendor blocking with automatic reinstatement when the block ends.

Process Studio

Low-code rules, with a safety net

Add custom fields and calculated values, and build visual rules that route approvals, hold steps, create tasks, notify people or call signed webhooks. Changes go through drafts, simulation, versioning and four-eyes publishing, and can never weaken the integrity rules.

Notifications

The right nudge, in both languages

Editable bilingual notifications by in-app message, e-mail and SMS, with a delivery log. Approval SLAs escalate automatically when a step sits too long.

The cycle

Fifteen steps.
One record.

The full cycle as the product runs it, and who acts at each step.

  1. Configure the entity and its cycle template

    Admin

  2. A department raises a request; it is approved and converted to a tender

    Officer · Director

  3. Vendors register and upload their documents

    Vendor

  4. Vendors are approved, with activity codes and grades

    Officer

  5. The tender is drafted and its pack checked

    Officer

  6. Approval, level by level — never by the creator

    Director

  7. Published; the gazette / CAPT notice is drafted and approved, and eligible vendors alerted

    Officer · Director

  8. Vendors buy the tender documents, where required

    Vendor

  9. Clarifications are asked and answered

    Vendor · Officer

  10. Sealed bids are submitted and receipted

    Vendor

  11. The tender closes at the deadline

    System

  12. The chair opens the bids

    Chair

  13. Compliance checklist, scoring and committee narrative

    Chair · Evaluators

  14. The award is recommended and approved; records are locked

    Chair · Director

  15. The audit chain is verified

    Auditor
Deployment model

One installation
per entity.

Each entity gets its own database, FileNet object store, Orchestrate instance, keys, committees, suppliers and branding.

Built on Node.js, TypeScript, React and PostgreSQL. It runs on OpenShift, and the public demo runs on Azure App Service. IBM FileNet and IBM watsonx Orchestrate are optional: without them TenderFlow keeps documents in a local file store and marks its AI features as not connected.

Security and access

Ready for the
security review.

The controls an entity’s security team will ask about first.

Two-step verification

TOTP codes with recovery codes. Switch it off, make it optional or require it — separately for vendors and for staff.

Staff network allowlist

Staff sign-in can be limited to approved networks. Vendors are unaffected.

Account lockout

Five failed attempts in fifteen minutes lock an account for fifteen minutes, with an administrator unlock.

Document protection

Tender documents can be view-only, or downloaded with a watermark that names the vendor on every page.

Dashboards and analytics

A dashboard for every role, procurement analytics, and a public board of the entity’s open tenders.

Arabic and English

Right-to-left Arabic and English throughout, notifications included.

Try it

Up and running
in five commands.

Explore the hosted demo, or run TenderFlow from the repository.

Local

Run it on your machine

Needs Node.js 20 or newer. From a copy of the repository, on Windows:

> copy .env.example .env
> npm install
> npm run gen-keys
> npm run build
> npm start

Then open http://localhost:4000.

Entities

Set up an entity

Create an entity with its English and Arabic names, check its configuration, or reset the demo data.

> npm run entity:create -- --code … --name-en … --name-ar …
> npm run config:check
> npm run demo:reset -- --yes

The demo ships with three fictitious entities to explore. For production, each entity is recommended its own OpenShift namespace, database, FileNet object store and Orchestrate instance.

Version 1.0.0-rc7 — a release candidate. Not yet verified against live systems: staff single sign-on with Entra ID and AD FS, and FileNet-stored originals in the protected viewer. Scanned PDFs need OCR before their data can be extracted.
