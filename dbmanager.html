Why it exists

Most database teams run more than one engine. Their tooling rarely admits it.

Built by KBM for mixed fleets
Six engines usually means six consoles. DBManager gives every server the same view.

A team that runs several engines ends up with one tool per vendor, and no single place to ask which server needs attention. KBM DBManager puts the whole fleet behind one screen, with the same questions answered the same way for every engine. And when a server cannot provide something, it says so plainly — requires privilege / configuration / license — and never fills the gap with invented data.

Capabilities

Everything a DBA checks,
for every engine.

From the first connection test to the audit record of the last change.

Fleet
Fleet · Onboarding · Topology

Add a server and watch it prove itself

A registration wizard walks through engine, connection, TLS and a least-privilege monitoring account, then runs a live, staged connection test: DNS, TCP, TLS, authentication, version, privileges and capabilities.

Onboard in bulk from CSV, JSON or a grid. Organise the fleet by environment, site, cluster, application and tag, and explore it as an interactive topology.

Every server joins in Monitoring Only mode by default.
Monitoring
Monitoring · Sessions · Replication

See what every server is doing right now

Connections, sessions, locks and blocking chains, throughput, latency, cache, I/O, replication lag and storage — shown in the same view for every engine.

History is kept in a time-series database, so you can scroll back from the symptom to the moment it started.

One screen for the first question on any incident: which server, and why.
Query performance
Query performance · Execution plans

Find the statement that got slower, and the plan that changed

Top statements come from each engine’s own statistics, with fingerprints and trends. Open estimated and actual execution plans as a graph, a tree or the raw vendor plan.

Regression and plan-change detection flag what moved; period-versus-period and plan-versus-plan comparison show by how much.

From “it feels slow” to the exact step of the exact plan.
Capacity

Know the day a disk fills

Storage forecasts per server, database and tablespace, built on a robust trend with a 90% band and a days-to-full figure.

Alerting

Alerts that know each server’s normal

Threshold, health and collector rules on latest values, window aggregates or deviation from a server’s own baseline. An inbox to acknowledge, comment, resolve and re-notify, recurring maintenance windows, and delivery by webhook, Slack, Teams or e-mail with retries and routing.

Backup & restore

Backups you have actually verified

Encrypted backups of the platform and of managed databases — PostgreSQL, MySQL, MariaDB, SQL Server, Oracle Data Pump and Db2 LUW — to local, NFS or S3-compatible storage. Policies, retention, verification, a restore wizard with impact analysis and a disaster-recovery scan.

Recommendations

116 rules, each with its evidence

61 performance and configuration rules and 55 security rules, common and engine-specific. Every finding carries its evidence and its risk, and shows a before/after outcome once it is resolved.

Security posture

A score for every server, and for the fleet

Privileged accounts, excessive grants, authentication and encryption checks, rolled up into a security posture score per server and per fleet.

Administration

Change control, built into the tool

Manage users, roles, grants, schemas and indexes through actions that are previewed, confirmed and audited. Administration is off by default: servers start in Monitoring Only.

Supported engines

Six engines.
Stated honestly.

Six engines are validated against real servers, and this list says exactly how far each validation went.

PostgreSQLSupported · reference adapter

Versions 12–17. Validated on 16.15: adapter, backup and restore.

MySQLSupported

Versions 8.0, 8.4 and 9.x. Validated on 8.4.11: adapter, backup and restore.

MariaDBSupported

Versions 10.5–11.x. Validated on 11.4.13: adapter, backup and restore.

Microsoft SQL ServerSupported

2016–2022 and Azure SQL. Validated on SQL Server 2022: adapter, backup and restore.

Oracle DatabaseSupported · no management packs needed

12.2–23ai, through the thin driver with no Oracle Client. Validated on 21c XE: adapter, Data Pump backup and restore.

IBM Db2 LUWSupported

Versions 11.1–12.1. Validated on 11.5.9.0: adapter and backup.

IBM Db2 for z/OSPartial

Versions 12–13 over DRDA (needs Db2 Connect). Awaiting validation on a real z/OS subsystem.

Oracle Diagnostics and Tuning Pack features — AWR, ASH, ADDM, SQL Monitor and SQL Tuning Advisor — are never queried unless you mark a server as licensed.

Architecture

Four containers.
Nothing exotic.

A React frontend served by nginx, a FastAPI backend, PostgreSQL as the control plane and VictoriaMetrics for metric history.

Deploy

Running in
a few commands.

On a laptop with Docker Compose, or on Kubernetes and OpenShift with the Helm chart.

Docker Compose

Try it locally

Needs Docker with Compose v2, 4 GB of RAM and port 8080 free.

$ git clone https://github.com/hbenabdalla/dbmanager.git && cd dbmanager
$ ./scripts/init-env.sh
$ docker compose up -d --build

Then open http://localhost:8080 and sign in as admin with the bootstrap password that init-env generated in .env. On Windows, run powershell -ExecutionPolicy Bypass -File scripts\init-env.ps1 instead. Back up DBM_MASTER_KEY: stored database credentials cannot be decrypted without it.

Kubernetes · OpenShift

Run it for the team

Two API and two worker replicas under the restricted Pod Security Standard. Images and chart are signed with cosign.

$ helm install dbm oci://ghcr.io/hbenabdalla/charts/dbmanager --version 0.16.0 \
    --namespace dbmanager --create-namespace \
    --set secrets.masterKey="$(head -c32 /dev/urandom | base64)" \
    --set secrets.bootstrapAdminPassword='<a strong password>' \
    --set secrets.postgresPassword='<a strong password>' --set secrets.timeseriesPassword='<a strong password>'

Add --set openshift=true for OpenShift restricted-v2. The deployment guide in the documentation covers high availability and configuration.

Version 0.16.0 — not yet 1.0. Still to come before 1.0: scale and security testing, accessibility, an upgrade drill from every 0.x schema, and a release candidate.
